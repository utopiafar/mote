# Mote HTML 交互原型：15 轮独立评估规程

- 规程版本：`mote-ui-prototype-v2`。
- 更新日期：2026-10-20。
- 本次对象：**HTML 交互原型 UI**。模型、同步、权限、任务处理和设备连接均以明确的 mock 状态呈现。
- 核心目标：首屏能理解产品用途，功能归属清楚、主次突出，重要功能可发现，原型中的导航、表单、反馈和恢复路径可走通。
- 覆盖范围：沿用现有源码盘点的 **20 类功能、78 个单元**，逐项核对原型中的呈现与入口。
- 当前状态：**R0 尚未评估，完成 0/15 轮。** 分数为 `null`，任务为 `not_run`。

本规程替代 `mote-ui-v1` 中针对真实业务闭环和原生设备的验收范围。本次直接使用本地 HTML、渲染截图、DOM 和原型交互执行记录推进。部署、真实模型调用、真实同步、系统权限和原生设备运行属于后续产品接入验证。

## 1. 方法与评价对象

参考 [Anthropic 的前端生成—独立评估循环](https://www.anthropic.com/engineering/harness-design-long-running-apps)：采用 Design quality、Originality、Craft、Functionality 四项标准，由独立评估反馈驱动多轮修改，保留中间候选。Mote 新增 Clarity，重点评估产品理解、功能发现和信息架构。

下文的权重、原型判定口径、覆盖要求和轮次安排为本项目的执行设计。

| 本次检查 | 可接受的原型实现与证据 |
| --- | --- |
| 导航与层级 | 点击后到达预期内容；当前位置、返回方式和分组关系清楚 |
| 表单与反馈 | 输入、校验、提交、取消、成功与失败状态可以演示 |
| 模型与问答 | 用 mock 展示未配置、配置完成、生成中、答案及来源跳转 |
| 同步与任务 | 用 mock 展示未连接、待处理、进行中、失败、重试及完成 |
| 权限与设备 | 用 mock 展示授权说明、拒绝、恢复及连接状态 |
| 多端设计 | 在 HTML 中渲染对应的客户端布局或视口，核对入口与视觉一致性 |

原型以简短、稳定的提示说明演示数据及模拟状态。功能性评分依据可执行的 UI 状态变化；可见成功反馈对应原型内的状态更新。

## 2. 功能清单与覆盖

- [feature-inventory.md](feature-inventory.md)：功能盘点说明。
- [feature-manifest.json](feature-manifest.json)：20 类、78 单元的覆盖分母。
- [schema.json](schema.json)：每轮记录格式。
- [rounds/r00.json](rounds/r00.json)：已归档的 R0 基线评估。

每个功能单元保留原编号，记录：原型中的所属分组、自然入口、呈现位置、主次级别、可演示状态以及证据。P0/P1 和核心/进阶分组沿用清单，在 R0 前核对适用性。

每轮检查改动单元及其相邻入口；R0、R3、R6、R9、R12、R15 核对全部 20 类和 78 单元。报告区分“已核对”“待核对”“入口缺失”“归属冲突”，保留完整分母。`coverage` 记录已核对数量；逐项依据仍引用清单编号与对应证据。

“不遗漏”要求所有单元在原型中有适当归属和可达入口；“不重复”要求同一功能的名称、主要管理位置与状态语义一致。上下文快捷入口可以共存。首屏优先表达产品用途与核心起点，进阶能力在所属分组内展开。

## 3. 角色与隔离

| 角色 | 输入 | 输出 |
| --- | --- | --- |
| 生成器 | 功能清单、规程、上一轮反馈 | 保存的 HTML 候选、具体改动、渲染及交互材料 |
| 独立知情 evaluator | 功能清单、规程、候选截图、DOM 和交互执行证据 | 五项评分、证据依据、问题、下一轮最高收益改法 |
| 全新首屏盲评 agent | 首屏渲染及自然语言任务 | 产品理解、感知到的功能、首选动作、困惑和探索记录 |

知情 evaluator 不参与 HTML 实现。可以自行操作原型，或独立审阅实际生成的渲染、DOM 和交互执行记录；每轮说明自己看到了哪些材料。

首屏盲评使用 `fork_turns="none"`，不看代码、文件目录、功能清单、设计说明、历史分数或旧反馈。先固定首屏回答，再提供原型探索任务。知情 evaluator 随后对照完整清单检查遗漏。

首屏问题：

> 这个产品主要帮你做什么？你觉得可以做哪些事情？第一次使用，你会先做什么？界面中的哪些内容让你这样判断？

任务只描述用户目标，例如“保存一段想法，稍后重新找到它”，或“看看连接失败以后该怎么继续”。任务不包含按钮名或点击顺序。

## 4. 五项评分

| 维度 | 权重 | 本次口径 |
| --- | ---: | --- |
| Design quality / 整体设计品质 | 20% | 布局、视觉语言与产品内容统一，主视图完整协调 |
| Originality / 原创性 | 10% | 设计决策适合个人上下文归档的内容和任务 |
| Craft / 基本功 | 15% | 字号、间距、对齐、对比度、状态、溢出和不同视口表现 |
| Functionality / 原型功能性 | 30% | 导航、表单、反馈、返回、失败恢复及 mock 状态变化可走通 |
| Clarity / 理解与信息架构 | 25% | 首屏理解、功能发现、重点突出、分组和命名清楚 |

各项取 0–4 整数：0 为已观察到的严重缺失；1 为主要目标受阻；2 为基本可用但有明显猜测或绕路；3 为清楚顺畅、无关键阻碍；4 为完整细致且复杂状态处理稳定。尚无评估依据时用 `null`。

总分为 `sum(weight × score / 4)`，五项都有分数后计算。每项理由引用具体截图、DOM 或交互证据。Functionality 的证据至少包含实际执行的原型交互记录；视觉与首屏判断使用渲染结果。

R0 用少量具体问题校准评分边界，固定后跨轮复用。阶段复核同一标准，隐藏候选轮次和旧分数后比较，减少分数随轮次自动上升。

## 5. 原型验收门槛

| ID | 门槛 | 通过口径 |
| --- | --- | --- |
| G-COMPREHENSION | 首屏理解 | 能说清聚合个人信息、归档后回看/检索/提问，并指出起点；最终 3 个新上下文至少 2 个通过 |
| G-DISCOVERABILITY | 核心入口可发现 | 无路径提示，最多 5 次导航操作找到合理入口；最终核心任务至少 2 个新上下文通过 |
| G-P0-COMPLETION | 关键原型旅程完整 | P0 原型导航、输入、提交/取消、反馈和适用的返回/恢复路径可演示 |
| G-FEATURE-COVERAGE | 20 类 / 78 单元覆盖 | 每个单元有明确归属、适当入口与呈现，关键单元有可演示动作 |
| G-NO-CONFLICT | 结构清楚一致 | 主要管理位置、名称和 mock 状态语义无冲突 |
| G-NO-BLOCKER | 原型关键阻断清零 | 核心按钮、路由和表单可用，没有导致核心操作中断的遮挡或死路 |
| G-DIMENSION-FLOORS | 分项下限 | Design / Craft / Functionality / Clarity 至少 3；Originality 至少 2 |
| G-VALIDATION-COVERAGE | 证据覆盖 | 阶段全清单核对有据可查；最终 P0 原型旅程有交互执行记录 |

任务状态使用 `not_run`、`blocked`、`pass`、`fail` 或有范围理由的 `not_applicable`。mock 的连接、权限和模型状态按原型表现判定。每轮可以发现失败并进入下一轮修正；完成迭代与候选通过门槛分别记录。

## 6. 每轮最小材料与记录

一轮须保存：

1. **HTML 候选**：独立保存的具体文件；`candidate_revision` 写实际路径与内容哈希，`parent_revision` 指向上一候选。优先使用单文件 HTML；引用资产时固定同轮资产版本。
2. **具体改动**：说明改了哪个入口、布局或状态，以及希望改善的用户行为。
3. **可见证据**：首屏和本轮改动区域的渲染截图，相关 DOM 及实际交互执行记录。记录视口、主题、初始 mock 状态、操作步骤和结果。
4. **独立评估**：五项分数与理由、已核对范围、具体问题、一个下一轮最高收益改法。

知情 evaluator 以其实际看到的材料填写评估。截图、DOM、操作执行记录均引用实际文件；没有观察到的状态留待核对。盲评材料只包含 UI 和自然语言任务。

本轮循环使用 WeasyPrint 静态排版材料与 jsdom DOM 交互执行记录。WeasyPrint 导出的图或页标为 `static_layout`，jsdom 执行记录标为 `interaction_trace`，并在说明中写明生成方式。视觉评分依据实际可见排版，交互评分依据执行步骤和状态变化。

`tasks` 同时承载旅程与门槛，`evidence` 保存证据引用，`coverage` 记录 20 类 / 78 单元的核对数量。每轮记录与 HTML 候选一一对应；修正文档、渲染重试和重复评分同一候选记为准备工作或 `recheck`。

每轮评估同时写入 `rounds/rXX.json` 和 `prototype/evidence/rXX/review.json`。前者使用统一 Schema；后者按维度保留简明理由与证据，汇总一个最高收益的下一项改法。候选标识、分数、覆盖数量和下一步在两份记录中一致。

## 7. 15 轮如何推进

**R0：** 保存基线 HTML，准备渲染/DOM/原型交互材料，完成知情评估和至少一次新上下文首屏盲评。R0 不计入 15 轮。

**R1–R15：** 每轮按上一轮实际发现选择最高收益问题，修改并保存具体 HTML 候选，重新生成材料，交给独立 evaluator 评估，再决定继续细化、调整方向或保留候选。

- 每轮：一个独立知情 evaluator 评估；至少覆盖本轮改动与相关核心路径。
- R0 / R3 / R6 / R9 / R12 / R15：至少一个新上下文盲评，并核对 20 类 / 78 单元覆盖。
- 最终：三个新上下文交叉比较至少三个保存的候选，轮换展示顺序并隐藏轮次。

建议优先解决产品理解与导航，再处理任务路径、状态反馈和视觉细节；具体改动由反馈决定。评估者每轮输出简明的五项评分、证据、主要问题和下一项改法。

## 8. 最终选择与交付

候选选择依次看：原型门槛、核心入口与旅程、逻辑清晰、整体设计与基本功。保留中间候选，按同一规程选出最合适的版本。

交付包含 HTML 候选、逐轮变化与独立评估、首屏盲评记录、20 类 / 78 单元覆盖及最终选择理由。本次结论对应原型的视觉、信息架构和模拟交互表现。

执行结果已保留 R0 基线及 R1–R15 的 HTML 候选、独立评审和正式记录。最终结论见 [final-report.md](final-report.md)。`schema.examples[0]` 继续保留为尚未执行的空白记录模板，不能当作本次实际进度。完成轮次与通过全部门槛分别记录，最终仍存在的部分完成项和 UI 问题不改写为通过。
