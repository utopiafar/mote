# Mote 现有 UI 迭代与独立评估规程

- 规程版本：`mote-ui-v1`。
- 初始状态日期：2026-10-20（UTC）。
- 目标：围绕现有功能完成约 15 轮实际 UI 改进，使产品用途一眼可理解、功能归属清楚、重要能力可发现、关键旅程可顺畅完成。
- 当前准备状态：源码盘点、合成数据运行环境和构建已就绪。
- 当前执行状态：**R0 实操受阻且尚未运行，已完成 0/15 轮；全部 UI 评分为 `null`，任务为 `not_run`。** Cloudflare 公网通道申请被自动审批明确拒绝，原因是用户尚未授权向外部披露测试 UI 及认证入口。未启动任何隧道。
- 本文件是执行规程。每轮实际状态、证据和决定以符合 `schema.json` 的记录为准。`rounds/r00.json` 与 Schema 的 `examples[0]` 同步记录此次 R0 的阻塞状态；静态规程审阅不计为 UI 实操或迭代。
- 执行状态与访问审批的具体范围见 [README.md](README.md)。

## 1. 方法来源与本项目的新增设计

来源：[Anthropic — Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)，发布于 2026-03-24。

原文前端实验采用四项指标：

| 原文指标 | 本文使用的中文名称 |
| --- | --- |
| Design quality | 整体设计品质 |
| Originality | 原创性 |
| Craft | 视觉与交互基本功 |
| Functionality | 实际易用性 |

原文让生成器和独立评估器共享标准，评估器用 Playwright 操作页面、截图、评分并提出批评。作者使用带详细评分的示例校准判断，循环 5–15 轮，按结果决定继续细化或调整设计方向，并观察到中间版本可能优于最后版本。

**以下权重、门槛、功能矩阵、盲测隔离、证据格式及执行频率均为本项目新增设计。** 原文另外讨论了全栈开发实验；本次评分保留上表的前端四项，并增加“理解与信息架构”。

## 2. 范围与计数

针对仓库内当前已有的 Central Web、macOS 和 Android UI，先按实际代码确认适用范围。每个平台分别记录实现与验证情况。Web 窄屏展示归入 Web 响应式验证；原生端旅程使用相应应用实际验证。

R0 是基线，R01–R15 是计划中的改进轮次，最终候选比较单独记录。约 15 轮是工作预算，实际问题决定各轮内容。

一轮被计为已完成迭代，须同时具有：

1. 对上轮反馈或基线问题的具体改进假设。
2. 已保存、可恢复的 UI 改动，以及候选版本标识。
3. 一个独立 evaluator 对运行中 UI 的实际操作。
4. 操作结果、截图或状态证据，以及按同一规程给出的评估。
5. 保留、修正、转向或舍弃该候选的明确决定。

运行环境恢复、重新启动、静态代码审查、重复检查同一版本，分别作为阻塞处理或 `recheck` 记录。它们不增加已完成迭代数。完成一轮评估也不要求候选通过全部门槛；发现失败并据此继续修改是有效迭代。

## 3. 建立功能—入口—旅程—结果清单

先交叉读取代码、路由、设置、客户端能力、相关文档及实际页面，建立稳定的功能编号。菜单只是证据之一，隐藏能力也要进入清单。

| 字段 | 记录内容 |
| --- | --- |
| `feature_id` | 稳定编号，例如 `F-RECORD-01` |
| `user_goal` | 用户想得到什么结果 |
| `priority` | P0 核心旅程 / P1 重要能力 / P2 低频进阶能力 |
| `surfaces` | 适用的平台 |
| `states` | 新用户、有数据、未连接、未配置模型、权限不足等状态 |
| `implementation_evidence` | 实现位置、现有测试、运行证据 |
| `canonical_home` | 主要管理位置 |
| `contextual_shortcuts` | 合理的上下文快捷入口 |
| `success_state` | 完成后的可见结果与实际状态 |
| `journey_ids` | 对应的完整旅程 |
| `blind_task` | 不含 UI 标签或点击步骤的自然语言任务 |

清单至少检查以下旅程族，并根据当前实现补齐细项：

- 记录内容、保存、再次找回。
- 手动导入、预览、处理、查看结果。
- 设置采集范围、权限、启停与状态。
- 文件及目录同步、待传状态、失败与重试。
- 浏览、筛选、搜索及打开原始内容和来源。
- 提问、阅读答案、沿引用查看证据。
- 记忆及复盘、与原始资料的关系和跳转。
- 外部来源、Coding 会话、MCP 的接入及使用。
- 模型等前置配置、修复缺失条件、返回原任务。
- 长任务、错误恢复，以及账户、设备、插件和设置。

“不遗漏”要求冻结清单内的能力有明确归属和可达入口；“不重复”要求同一功能的主要管理位置、名称和配置状态一致。多个上下文快捷入口可以共存。首屏突出核心用途和起点，进阶能力在相应分组内渐进展开。

清单标明尚未实现、当前关闭和已实现但隐藏的能力。评估针对本次范围内的现有能力，界面说明须匹配真实行为。

R0 前冻结清单与规程版本。新增或改变需求时记录版本差异；候选之间的比较使用相同口径。

## 4. 角色与信息隔离

| 角色 | 允许看到的信息 | 负责输出 |
| --- | --- | --- |
| 生成器 | 功能清单、规程、代码、已提交评估 | 可运行候选、改动与假设 |
| 独立 evaluator | 完整清单、规程、运行环境、已冻结的盲测记录 | 实操结果、功能覆盖、门槛、评分与修复排序 |
| 全新盲测 agent | UI、合成测试账户、自然语言任务 | 第一印象、实际选择、路径、犹豫、错误和结果 |

生成器不替代独立 evaluator 评分。独立 evaluator 可以延续经过校准的评估上下文，但不能参加该候选的实现。

盲测使用 `fork_turns="none"` 的新上下文；不提供仓库代码、README、功能清单、路由表、设计理由、上轮反馈或分数。先冻结盲测原始回答，再让 evaluator 对照功能清单。

### 4.1 首屏理解

先只展示初始屏幕，保持截图、视口和初始数据状态可比。提问：

> 这个产品主要帮你做什么？你认为现在能做哪些事情？如果第一次使用，你会先做什么？请指出界面中支持你判断的内容。

保存原始回答及其界面依据。随后才允许探索页面。本项称为“首屏理解测试”，记录 agent 实际回答与样本数。

### 4.2 无提示任务

任务例子：

> 保存今天的一段想法，稍后重新找到它。

> 找到之前保存过的一份资料，并查看它来自哪里。

任务描述只写用户目标。逐步记录首次选择、实际导航、返回、错误入口、求助和完成状态。可接受多条符合用户直觉的有效路径，不要求复现设计者唯一预设路线。

### 4.3 执行频率

- **每轮：** 一个独立 evaluator 操作改动旅程，检查受影响的 P0 旅程，并输出证据。
- **R0 / R3 / R6 / R9 / R12 / R15：** 至少一个全新上下文的盲测；同时核对全功能清单的可达性和本阶段旅程覆盖。
- **最终候选比较：** 三个全新上下文独立比较候选，至少包括三个已保存候选；隐藏轮次、旧分数和设计者解释，轮换候选展示顺序。

同一浏览器的不同标签可能共享 Cookie。阶段盲测和普通账号切换串行执行，并在交接时确认账户与测试数据状态。独立标签用于隔离导航；需要同时保留不同登录状态时使用独立浏览器配置。生成器可以并行修改代码，浏览器由当轮 evaluator 单独操作。

## 5. 评分与校准

| 维度 | 权重 | 评估依据 |
| --- | ---: | --- |
| Design quality / 整体设计品质 | 20% | 视觉语言、内容与布局形成统一产品 |
| Originality / 原创性 | 10% | 设计决策适合 Mote 的内容和任务 |
| Craft / 基本功 | 15% | 字号、间距、状态、对比度、焦点、溢出、响应式 |
| Functionality / 旅程可用性 | 30% | 任务成功、前置条件引导、真实结果、恢复路径 |
| Clarity / 理解与信息架构 | 25% | 产品理解、功能发现、主次、命名、归属 |

各项使用 0–4 的整数：

- 0：经实际检查，该维度对应的能力完全缺失或严重失效。
- 1：主要目标受到严重阻碍。
- 2：基本可用，存在明显猜测、绕路或不一致。
- 3：目标清楚、常见旅程顺畅，无关键阻碍。
- 4：完整细致，复杂状态和边缘交互表现稳定。

**尚未评估用 `null`；`0` 仅表示实际观察后的最低分。** 总分为 `sum(weight × score / 4)`，仅在五项均已评估时计算。每项理由必须指向证据。原始门槛及旅程结果与总分并列展示。

开始评分前，固定少量高、中、低质量的校准样例、分项理由和边界案例，并由独立 evaluator 试评。尚无用户直接给样例打分时，记录为团队初始校准。R3 / R6 / R9 / R12 / R15 用同一锚点抽查；发现尺度漂移时修正规程版本并复评待比较候选。

## 6. 硬门槛

| ID | 检查项 | 判定口径 |
| --- | --- | --- |
| G-COMPREHENSION | 首屏理解 | 阶段盲测能说清聚合个人信息、归档后回看/检索/提问，并指出可执行起点；最终三个新上下文至少两个通过 |
| G-DISCOVERABILITY | P0 入口可发现 | 无路径提示，最多 5 次导航操作内找到合理入口；最终每项 P0 至少两个新上下文通过 |
| G-P0-COMPLETION | 核心旅程完成 | 适用 P0 旅程全部实际完成，最终结果有证据 |
| G-FEATURE-COVERAGE | 重要功能无遗漏 | 清单内所有适用 P0 / P1 功能都有清楚归属、可达入口和对应证据 |
| G-NO-CONFLICT | 结构无冲突 | 没有相互矛盾的主要管理位置、配置状态、标签含义 |
| G-NO-BLOCKER | 关键阻断清零 | 阻止核心任务、丢失用户输入、主要操作无效果的问题为 0 |
| G-DIMENSION-FLOORS | 分项质量下限 | Design / Craft / Functionality / Clarity 至少 3；Originality 至少 2 |
| G-VALIDATION-COVERAGE | 验证覆盖完整 | 所有适用 P0 已执行；范围中的 `blocked` / `not_run` 明确保留 |

每轮评价按当前范围记录门槛。全产品通过须覆盖完整适用清单，不能把局部通过扩大为全产品通过。`not_run` 表示尚未执行，`blocked` 表示执行受阻，`fail` 表示已有失败观察，`pass` 表示已有通过证据；不适用使用 `not_applicable` 并说明具体范围依据。

阶段盲测只有一个样本时报告 `1/1` 或 `0/1`；最终交叉比较报告原始计数。5 次导航操作用于入口发现，完整任务长度按其实际前置条件另外记录。

## 7. 证据与记录要求

每轮记录至少包括：规程和清单版本、候选和父版本标识、改进假设、实际改动、适用平台与状态、独立 evaluator、盲测状态、分项评分、门槛、旅程、问题和下一轮决定。

## 8. 约 15 轮的反馈驱动执行

R0 的源码盘点、合成数据运行环境和构建已就绪。浏览器访问方式获得相应授权并可用后，确认适用旅程与评分锚点，运行基线并发现最重要问题。**R0 之后才确定 R1 的具体改动。**

| 轮次窗口 | 优先覆盖的内容 | 独立检查 |
| --- | --- | --- |
| R1–R3 | 产品定位、主导航、初始状态和第一步 | 每轮实操；R3 新盲测及清单核对 |
| R4–R6 | 记录、导入、设备采集、关键入口 | 每轮实操；R6 新盲测及清单核对 |
| R7–R9 | 文件/目录同步、浏览搜索、提问与证据 | 每轮实操；R9 新盲测及清单核对 |
| R10–R12 | 记忆复盘、外部来源、MCP、模型与插件设置 | 每轮实操；R12 新盲测及清单核对 |
| R13–R15 | 进度和恢复、跨页面一致性、原生端和主题、集成问题 | 每轮实操；R15 新盲测及完整复测 |

这张表是覆盖窗口，不是预先安排 15 个独立提交。每轮开始时：

1. 按关键阻断、功能遗漏、旅程困难、结构清晰、视觉细节排序上轮发现。
2. 选择一个相关问题集合，写明希望改变的用户行为和可验证结果。
3. 生成器修改真实界面，保存候选。
4. evaluator 独立操作，评价改动旅程和受影响的核心路径。
5. 有阶段盲测时先冻结盲测记录，再做清单映射。
6. 更新问题状态和候选选择；由结果决定下一轮。

连续若干轮改动没有改善同一问题时，重新检查信息分组或交互假设，必要时切换方向。保留有效的核心路径；设计变化按证据评估，不以变化大小计质量。

## 9. 最终比较与交付

至少选取三个可运行、已保存候选，由三个全新上下文在相同数据状态下比较。展示顺序轮换，隐藏轮次与历史评分。每个上下文完成首屏理解和约定的 P0 任务，再由有清单 evaluator 汇总功能覆盖。

选择顺序：硬门槛、核心旅程完成与入口发现、逻辑清晰、整体视觉品质、实现复杂度。中间版本可以成为最终候选；必要的后续修复单独保留证据。

交付包括实际变更、最终候选标识、功能矩阵、真实完成的轮次、每轮发现和决策、独立评估证据、各平台验证状态，以及仍待处理的具体事项。全部状态按实际填写。

## 10. 阻塞处理

浏览器、运行环境或原生端不可用时，记录具体阻塞和可继续的工作。仍可整理清单、规程、代码和合成 fixture。只有实际操作恢复后才填写相应的实操评分和通过结果。

本次阻塞发生在申请通过 Cloudflare 建立公网通道、供外部浏览器访问测试 UI 及认证入口时。自动审批明确拒绝该操作，理由是用户当前授权未覆盖这些入口的外部披露。未启动任何隧道。

下一步是在已授权且能够访问本地 UI 的环境中执行 R0；若采用上述公网方式，须先取得对应的用户授权。当前先完成静态规程与格式核对。

R0 记录的总状态为 `blocked`，五项评分和加权分数均为 `null`，所有门槛和旅程保持 `not_run`，独立 evaluator 实操为 `not_run`，迭代计数为 `false`。源码盘点、运行环境及构建准备工作单独记录；UI 实操仍为 0/15 轮。
