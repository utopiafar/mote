# 遮名候选有界比较 A

## 结论

就提供的三类桌面画面，在“逻辑清晰、范围可信、重点与视觉”合并判断下，我的排序为 **stone > reed = pine**。stone 的领先主要来自来源任务页更明确的范围说明；三组首屏基本同构，视觉表现没有明显整体胜负。reed 与 pine 的可见差异不足以支持可靠的总体先后。

这不是全产品排序，也不是完全无暴露的盲测。我在本次比较之前，已看过当前版本的桌面首屏与手机空状态，并完成过保存决定、离开、按关键词找回全文的任务。该熟悉度可能影响我对相似布局的阅读速度。本次未读标签映射、候选 HTML、实现源码、其他评估报告或分数，未按版本轮次推断好坏，也未把此前任务成功自动归给任何遮名候选。

## 方法与冻结边界

按指定顺序 **reed → stone → pine** 查看，每组依次读取 `library.png`、`source-task.png`、`memory-result.png` 和相应可见 DOM JSON。读取路径仅限 `evidence/neutral-comparison/` 下这三个标签。未开启浏览器交互或新的任务旅程；首次访问记录、自然任务日志、截图、`first-look.json`、`task-result.json` 及 `blind-r18-a.md` 均未因比较改写。

DOM JSON 仅用于核对可见文本和控件标签；不能从静态控件存在推出操作确实有效。以下提到的范围、记忆输入及完成状态均是界面所表达的内容，未验证真实数据或后端。

## 具体可见差异及其含义

### 1. 首屏功能结构接近，不能据此宣称一组“重做了信息架构”

三个 `library` 画面都以“资料库”为标题，首屏文字完整回答输入、保存后的查找/提问用途，以及资料、记忆、洞察的大致区别。左侧“资料／整理与回顾／原始记录／导入管理”分组、六条样例资料和右上角“随手记／添加内容”均相同。这部分应判为相当。

stone 的可见新增是“全部设备”筛选。它让列表里已有的“网页／Mac／中央”元信息有了可直接操作的对应入口，也增加了首屏控件数量。reed 与 pine 的搜索框更宽，但我没有证据把少一个筛选解释为缺失关键功能，或把多一个筛选解释为首次理解更好；需要结合具体找回任务决定。

对应材料：`reed/library.png`、`stone/library.png`、`pine/library.png` 及同名 JSON。

### 2. stone 的范围说明更容易审查，但截图不能证明数字真实

stone 把保存数量和范围解释放到来源名称下面，先告诉我“当前这个来源有多少”，再告诉我其他来源内容仍属于各自范围。这样阅读“查看已保存资料”时，我更容易预期它针对的是当前来源。

reed 与 pine 的 `source-task` 可见文字相同，均把“最近一次读取”与“已归档的 12 份资料仍可阅读”放在一行。授权过期但以前保存的资料可读，在概念上没有矛盾；问题是这组材料的 `library` 同时写“全部资料”“6 份资料”，没有解释 12 和 6 的计数关系。若这些画面属于同一个账号和相同时间范围，这个差异会让我犹豫是否正在比较不同范围。静态截图不能排除它们来自不同快照，也不能证明任何数字实际错误；它能支持的是“范围和计数需要解释”，不能支持“真实数据丢失”的结论。

stone 的“0 份”也只是 UI 声明，我未打开其资料入口核对。因此 stone 获得的是**表达更清楚、较容易检查**的优势，不是后端真实性认证。

三组“这次读取的范围”仍都只写“所选飞书文档与工作日历”，没有在这些画面直接列出具体文档、日历或所选数量。三组都有“查看来源设置”，但该入口是否展示了精确清单，本次无法判断。

对应材料：三个标签的 `source-task.png`、`source-task.json`，以及同组 `library` 中的 6 份资料计数。

### 3. 记忆输入文字不同，不能只凭这个差异断言纠正是否丢失

reed 的“本次采用的记忆内容”为“偏好入口简洁、按任务组织的界面。”；stone 与 pine 还显示“复杂设置放在相关上下文里。”stone 与 pine 的整份记忆结果可见文本相同。

新增一句使输入内容更具体，但本次材料没有提供用户之前输入或纠正的原始文字。我不能据此断言 reed 丢失纠正，也不能认定 stone 或 pine 完整保留了纠正。三个结果页都声称“当前记忆保留你的纠正”，这个声称需要前后文字或交互才能验证，本次不补测。

三组都把输入、核对 1 份依据、生成补充建议分开，并把原文名称直接放到核对入口中。这能支持“用户看得到系统采用什么、输出什么、去哪核对”的判断；无法单凭截图验证建议确实采用了输入，也无法验证按钮去向。

对应材料：`reed/memory-result.png`、`stone/memory-result.png`、`pine/memory-result.png` 及同名 JSON。

### 4. 视觉差异应保持小幅判断

stone 来源任务页多了两行数量与范围说明，恢复按钮比另两组略下移，但仍在同一屏且保持主要按钮样式。多出的解释是有用途的信息，没有造成明显视觉拥堵。reed 与 pine 的来源页内容更短，空白更多；在本任务里，更多空白不足以抵消范围说明的不足。

三组记忆结果页的绿色结果区域、紫色输入引用边线、底部核对入口基本相同。首屏也都保留了较长的资料子导航。我对“来源／资料出处／原始采集记录”之间边界的首次困惑，在这些截图中没有看到一组比其他组更明确地解决，因此不重复给任何候选加分。

## 排序的强度与不可判断项

**较有把握：** 三组首屏用途解释相当；stone 的来源数量及范围文案更明确；reed 与 pine 的来源任务文本相同；stone 与 pine 的记忆结果文本相同；stone 首屏多一个设备筛选。

**有限判断：** 综合排序 stone > reed = pine，权重主要放在来源范围可理解性，而非风格偏好。若只比较首屏视觉或记忆结果的结构，三组应并列。当前证据不支持把 pine 排在 reed 前或后。

**无法判断：** 来源计数真实性、按钮真实去向、授权恢复、筛选行为、记忆纠正是否真的保存、此前输入是否一致、跨会话持久化、移动端交互及真实后端。没有用版本轮次、未见功能或已经完成的另一条旅程替这些证据补空。
