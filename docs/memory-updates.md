# Unified extraction and versioned memory review

This change closes MEM-01 and MEM-03 and supplies the independent action-cue input for ACT-03. It introduces no intent keyword dispatch. Models interpret original evidence and propose semantic relationships; the host checks exact original quotes, scope, evidence versions, bounded output, and the internal review receipt. Reviewed Memory becomes active automatically. Calendar actions retain their separate owner/device confirmation contract.

## Behavior

- A complete segment of at most 12,000 original text characters produces one shared artifact with a summary, events, memory candidates and calendar action cues. The JSON response is bounded to 64 KB. Empty candidate arrays are valid. Original archive search remains available for facts not selected into the artifact.
- Memory batches reuse candidates whose full original quote ranges fit the batch, then retain independent review. Partial ranges and legacy artifacts explicitly fall back to bounded original extraction. Action processing independently consumes complete artifacts before any memory is published, at most eight cues at a time, with a durable checkpoint. A cue may cite multiple observations in the segment. Empty action output does not invoke the relationship model. Long originals/file chunks without a complete segment retain bounded original processing.
- Actions use only quote spans plus the read-only, paged prior-action catalog to decide duplication or update/cancel/complete relationships. All semantic proposals still need owner/device confirmation. They do not have calendar mutation tools.
- Memory relationships contain a target ID, fingerprint and version. Contradictions preserve both claims; supersession is applied atomically with a version-bound reviewed Memory commit. Project scope cannot acquire another project or automatically promote a session to a project/global rule. Original and replacement records remain separately readable.
- Current memory reads respect explicit validity dates and reviewed supersession. `includeHistory` and `asOf` support historical inspection. Direct references retain access to the historical content. A correction replaces its specified claim, not unrelated facts in its original source.
- Owner corrections atomically create an original user note and a new confirmed memory, preserving the selected memory's project/session applicability. A concurrent or stale correction loses without leaving a stray note. Automatic extraction cannot commit a stale target version over that correction; any later replacement must retrieve the correction proof and pass the same current evidence and scope checks. External capture/note routes reject the host-owned correction metadata field before any batch member is written.
- The memory UI shows automatically applied relationships and validity, supports active correction and historical navigation, and refreshes its time boundary after adding a correction. This fixed an observed renderer failure where the newly created correction fell outside the page's old `before` timestamp.
- Large shared artifacts expose summary, original citation IDs and product counts within the ordinary 24 KB detail budget. Duplicated candidate bodies are omitted from this read projection and remain available to the dedicated consumers; the projection marks the omission.

## Remaining validation boundaries

Native EventKit/Android calendar-provider writes under real user permissions, Gmail account authorization, and physical-device checks were not performed by this subtask. The native mutation logic is covered by generated host/client fixtures and compile/type checks. Calendar completion is a Mote-side resolution; it does not invent a native calendar “complete” operation. A native operation with uncertain outcome is only reconciled; it cannot receive another write grant simply because a device lost its local ledger.

## Automatic activation and deletion intent (2026-09-27)

A new candidate remains private to extraction/review until its independent model review and host validation succeed. The commit persists it as `published` and applies `supersedes` within the same transaction, including the batch checkpoint. The review receipt binds the exact final answer and deletion-policy snapshot. Changed original fingerprints, relation versions, authorizations, cancellation or a concurrent Memory deletion reject the commit. Integration records its own applied parent versions in its checkpoint so one successfully completed domain does not invalidate the other domain or get rerun after restart.

Legacy `proposed` cards with a recorded independent review, still-current exact quoted proof and valid relation versions can activate on startup. Cards lacking that evidence remain inspectable legacy navigation, with no user confirmation queue. Their old extraction checkpoints are released so explicit reprocessing can obtain a fresh review; an identical new reviewed result activates the existing card. Startup performs no model call. Restored portable cards remain `stale` and require processing.

Deleting a Memory keeps original materials. The host stores the deleted conclusion, bounded quoted proof and original dependencies privately; the record is neither indexed nor available as query evidence. Existing consolidated descendants linked through `relatedMemoryIds` become stale. Merely pointing to the deleted historical card through `supersedes` or `contradicts` does not invalidate a successor with its own original proof; deleting a replacement also does not reactivate the older superseded card. This is not a whole-vault semantic removal of every independently supported similar claim. Later candidates sharing original content or source lineage receive a separate read-only model comparison. That model decides whether the conclusion is the same and identifies genuinely new supporting evidence. The host rejects old identities and old exact proof as new evidence, then suppresses same-conclusion candidates without new support. Independent evidence on another date can establish a new occurrence even when its words repeat. Unrelated new citations do not themselves reopen a rejected conclusion.

Identity uses original file bytes when available, otherwise source event time plus text and stable source/external identity. Strategy, model, Memory ID, index and file-chunk IDs do not define freshness. A source revision containing only an unrelated append cannot reintroduce the unchanged old proof. Independently imported records that lack both preserved original time and stable source identity cannot be proven to be copies; this remains an explicit provenance limitation, rather than a lexical guess. Semantic equivalence/relevance remains a model judgment and must be evaluated separately from fixture transport/state checks.

Only related deletion records are disclosed to the review model, after current evidence authorization. Host-only derived-context dependency IDs are rechecked at model admission and completion without becoming new raw evidence seeds; source tombstones and local-only policy changes revoke disclosure. An unrelated local-only deletion never blocks or leaks into another task. Deleting or expiring one supporting original removes that dependency and all stored proof quotes from the rule. While other original dependencies remain, the compact rejected conclusion persists as an independent owner deletion instruction so the remaining old evidence cannot recreate it. This is not a claim that removing one original also erases the separately retained owner instruction. Removing the final dependency clears the whole rule. Explicitly forgetting an archive-backed source erases every deletion rule involving that source in the same transaction, including mixed-source conclusions whose other originals remain. This stronger privacy action also removes those mixed-source regeneration constraints; ordinary retention and index/material rebuilds preserve the applicable rules. Portable text archives include these records and verify dependencies, content identities and quoted text on import; typed file/Material archives retain the pre-existing complete-backup requirement. No lossy typed-file JSON export has been added.

Rules retain `derivationSourceIds` separately from the surviving evidence dependencies. These are source identities, with no removed original text. Ordinary pruning keeps them, so a later explicit source forget still finds and erases a mixed-source rule after that source's originals have expired. New rules carry `sourceLineageComplete: true`. Migration and old portable imports recover only identities still present in retained dependencies and carry `false`; they cannot reconstruct a source already removed before this metadata existed. Portable archives preserve the recorded lineage and reject a claimed complete lineage that omits a verifiable current source. Extra historical identities without retained originals are preserved as supplied owner-rule metadata, not presented as independently verified evidence.

Deletion rules and their dependency identity payloads count toward the logical storage quota. Source lineage is included once in the rule JSON's UTF-8 size. Reservations match the ledger's UTF-8 payload accounting, existing rules are backfilled when the tables join the ledger, and removing rules/dependencies releases that capacity transactionally.

`memory-automatic-deletion.test.ts` and the added file/integration cases cover automatic activation, historical values, correction/version races, cancellation, restart, cache invalidation, paraphrase verdicts, duplicate imports, changed strategies, new evidence, unrelated private records, old proof in revised originals, descendant invalidation, portable tamper rejection and raw retention. Scripted semantic verdicts prove host enforcement, not live-model semantic accuracy.

The complete deletion comparison has a five-minute host deadline across all candidate/rule comparisons and follows the parent cancellation signal, including for a model that ignores abort. It never silently skips unchecked rules; timeout leaves the batch retryable through the existing typed timeout path and saves no candidate/checkpoint. This execution protection is separate from flexible token/performance objectives.
