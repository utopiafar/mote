# Four historical text records and current recovery boundaries

Read-only metadata inspection mapped four archived text records to two actual extraction failures in the historical run035 task. Both persisted as `failed / extract / provider_timeout`, attempt 2, after earlier subdivision. Neither target has an exact completed checkpoint or a complete extraction draft. The task's other 12 batches and their completed work remain reusable. Its 32 receipts contain eight failures; four failed calls lack usage, and reported failed-call usage of 94,762 tokens is only a lower bound that cannot be allocated uniquely to these two targets.

A wholly generated probe checked current public behavior without opening or recovering the original database. A synthetic old raw-input task starts without provider admission but retry is rejected by the current published-Material guard. Current Memory input requires the formal Material identity; publishing a Material does not make its old raw SourceItem ID a valid Memory input. This does not justify bypassing the guard or adding general legacy compatibility.

In a separate generated Material-anchor control, host calls to retry and pause in the same JavaScript stack admit no provider and preserve the 12 completed batches and 36 checkpoints. Changing the selected timeout from 300 to 600 seconds updates the native job configuration, but does not disable measured-deadline subdivision: three chunks become two plus one, while the single-chunk target remains unsplit. Separate HTTP retry/pause requests do not provide that zero-admission guarantee; the generated retry request entered one deliberately failing stub before its response.

The Material control is a hybrid fixture with fabricated legacy history and omitted modern input-plan fields. Its new child became `invalidated / evidence_changed`; the cause is not established as a product defect. The observation and all earlier fixture construction failures are retained. This probe is not a successful old-database migration, native current-job subdivision validation or semantic quality result. It used one intercepted stub, zero real models and zero network attempts, and changed no product code or historical data.

Subsequent independent static review traced that invalidation to the fixture's removed per-batch Material pins. After splitting the parent, the legacy fallback derives scope from the now-smaller parent and produces empty references for the child; the Material guard then rejects it. Native current creation saves per-batch scope and does not use that fallback. No compatibility fix is justified by this hybrid fixture. Existing pipeline tests cover timeout subdivision, restart and successful child completion, but their raw-record fixture does not enable the formal Material gate; they are not evidence for the complete Material/recipe path. No additional test was run for this static review.

The least invasive candidate for actual recovery is to retain the old task, completed history and costs, resolve only the four originals through current formal Materials, then create a separate bounded task if its scope is authorized and validated. No actual remapping, preparation or model recovery has been performed. External evidence is `ROOT_SAFE_memex-four-gap-diagnosis-001.json` and `ROOT_SAFE_memex-legacy-retry-generated-delivery-001.json` in the September 27 goal directory; personal records and raw evidence remain outside Git.
