# 0.0.71 validation

This DEV release includes the real-context validation work since 0.0.70 and the final imported-attachment composition repair. Detailed progressive observations, including failed native runs, are in [Goal validation](../goal-validation.md). Personal originals, private manifests, model answers and native reports remain outside the repository.

## Final attachment repair

Archived attachments can be explicitly admitted through an owner-only API into the existing file store, execution engine and processing pipeline. The host verifies the source declaration, retained parent link and exact original bytes. It does not upload the bytes again or classify the source semantically. A processor must opt into content-only extraction reuse; original hash, MIME, processor identity/version, declared settings and model version must match. Forced extraction bypasses this cache. Corrections, speaker confirmations and summaries are not copied as raw extraction.

Formal source materials combine the authored caption and processed attachment blocks. Each selected attachment exposes its own named output and preserves original-pixel geometry and provenance. Independent consumers retain stable input fingerprints while another attachment fails or recovers. Attachment processing receipts no longer duplicate the parent in Agent timelines. Parent deletion or revoked linkage fences reads and late processing results.

Seven generated integration tests cover shared OCR with independent personal/Coding Memory recipes, failure isolation and recovery, owner/collector authorization, exact retained relationships, cache opt-in/settings/version changes, no automatic historical admission after restart, partial OCR coverage, and deletion during in-flight OCR. The generated Memory adapter validates composition and host contracts; it is not evidence of live-model semantic quality. Sixty related file, privacy, evidence, material and Memory-composition regression tests pass.

The opt-in native composition check uses a new isolated copy of a previously completed OCR vault and imports one previously authorized complete authored record with its exact linked image through the normal sandboxed source-pack API. The final result contains 176 evidence blocks, including 175 image-location blocks, in one two-member material. The caption input fingerprint stays stable. The existing raw OCR artifact is reused; original image bytes and caption hashes are unchanged; restart preserves the combined input fingerprint. The check makes zero new model calls and zero new extraction requests. It does not generate new Memory, evaluate answer quality or exercise a browser or physical device. The source has no timezone, so the explicitly configured offset remains a test assumption. This is a development sample, not held-out data.

## Release checks

The first release check overlapped the version rebuild: a desktop ingestion test exceeded its existing 30-second limit, and MCP fixtures rejected mismatched web/server build identities. Failed handshakes also exposed fixture cleanup registered too late; cleanup now runs even when transport setup fails. The shared reader tests pass independently. The final full check runs after the build has completed, with the original timeout and acceptance rules unchanged. The final `npm run check:local` (private log 054) exits 0: desktop 345, server 859, web 123, Agent 138 and shared 70 tests pass, alongside type/i18n, diagnostics, local-inference, worker, CLI and runner checks. One server and one Agent test are skipped by their existing conditions. Server/web production builds, release asset verification and release-version verification also pass. The release workflow separately builds and verifies the Mac DEV ZIP and Android development APK, including their expected identities and signing requirements. It does not run the full local test suite. Product packages, lockfile and Android version metadata are synchronized to 0.0.71 / versionCode 82.

## Remaining limits

- The preceding three real image queries did not pass the complete image-answer rubric. The latest reached the 120-second limit after receiving the image; a successful attachment composition does not convert that query into a success.
- This release does not claim completion of actual Memory/insight benefit, audio accuracy across the input distribution, held-out or whole-input validation, large-data UI/device acceptance, or ordinary Ask latency/cost targets.
- Attachment admission is currently an owner API, without a dedicated UI button. Reading an image or installing a processor does not authorize bulk historical processing.
- The broader Goal is paused at the user's request after the current repair and release. Remaining work is preserved for a later explicit resume.
