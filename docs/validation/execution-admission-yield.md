# Execution admission and event-loop progress

The user journey is a bulk import whose file and Memory work includes many configuration/readiness waits while other files are being processed. Admission failures can settle synchronously. Repeated microtask completion wakes can keep scheduling more waits without allowing readiness timers, HTTP responses, provider callbacks or the 10-second lease renewal to execute. Work can then lose its 30-second lease before its configured processing deadline.

The executor retains admission authority, durable pool capacity, per-operation fairness, retry times, attempt bounds, input validation and commit fences. An admission wait yields after its decision is committed, with no transaction or running lease held; this applies before either background continuation or an explicit drain can pump again. Completion wakes are coalesced within the same turn. Domain processing, model choice, privacy and retention rules remain unchanged. No architectural responsibility is superseded.

`apps/server/test/execution-event-loop.test.ts` creates a generated backlog of 64 admission waits with a short retry interval and measured synchronous work per check. A separate provider callback and readiness timer must run, all admission waits retain zero attempts, and the provider commits successfully. It covers background continuation and explicit drain separately. A parent process enforces the deadline because an in-process timeout cannot diagnose a starved event loop. The original background continuation exceeded that deadline; the revised implementation must pass both modes.

Existing execution-engine, deadline-cleanup, shutdown/restart, resource serialization, file-processing and image-processing tests cover the surrounding lifecycle and fencing contracts. Fixture results establish scheduling behavior, not real-model output quality, media accuracy, production throughput or physical-device validation. Those require separate observation after deployment.

The projection triggers also need the inverse `(step_id, active, operation_id)` membership index. The primary key begins with the operation ID and otherwise requires a full membership scan for each state/lease update. A private snapshot benchmark compared identical rollback-only updates before and after this index, and verified that SQLite changed from a table scan to a covering-index search. The existing thousand-original independently reviewed coverage journey validates the surrounding bulk workflow; benchmark timings do not establish a production throughput guarantee.
