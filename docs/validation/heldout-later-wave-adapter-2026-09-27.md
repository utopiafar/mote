# Heldout later-wave ingress and extraction adapter

This change adds bounded later-wave ingress and one-batch extraction. It also exposes explicit CLI dispatch to the separately validated integration module. Ask execution and answer evaluation remain absent; the corpus, questions, rubric, product code, model, original experiment identity, and initial batch pins remain unchanged. All development runs use separate mechanical sources and stub agents; no heldout semantics are read by the implementation agent.

The immutable initial `Manifest` remains the experiment root. A new `PhaseManifest@1` references its path and SHA, the preceding executor manifest, applicable offline validation, current runner hashes, and the canonical parent snapshot plus ledger head. Its task is either zero-admission ingress or one extraction batch. Every imported runtime helper is explicitly included in executor pins. Product source, compiled libraries, Node realpath/binary/version, Codex binary, model settings, and source/evaluation freezes remain bound to the original experiment.

`stage-ingress-freeze` only writes a new manifest. The existing supervisor subsequently invokes `stage-live`, which verifies the manifest, holds the same external ledger, copies the preceding canonical checkpoint, and delivers only the next wave through the ordinary Source API. Exact repeats must return the prior identity and leave Coding revisions unchanged. Real receipt timestamps remain real; authored and observation timestamps remain unchanged. Existing capture/version rows and archived original contents are preserved; the exact new-original counts must match the delivered delta. Each Coding delivery is drained through the normal pipeline. Only new or revised Material revisions enter the next paused job, using both original recipes and the original 12,000-character batch setting. A changed batch count is a stop, not a reason to alter the plan.

Ingress creates an immutable `WavePlan`, including the actual paused job and batch pins, context time, bindings, settings, and protected source-table hash. Its stage has zero provider admission, and the final closed database must contain no new usage IDs. A successful ingress advances the same append ledger and canonical archive head. `stage-extract-freeze` then freezes exactly the next pending batch. `stage-live` reuses the existing extraction runner, including the synchronous running-projection pause, unique logical admission, independent review, durable generation draft, failure stop, closed receipt reconciliation, and immutable parent check. Limits remain two outer admissions, 300 seconds each, 720 seconds overall, concurrency one, no outer retry, and cumulative planning cap 124. Empty cached output may consume zero calls; unused allowance does not start another batch.

The ledger's old wave-1 events remain unchanged. New successful `stage-close.phase` metadata records kind, wave, context time, archive head, total/next batch, evaluated-pair count and optional WavePlan reference. `phaseCursor` derives state from the whole hash chain. Ingress, extraction and integration advance the canonical archive. Evaluation advances only its question cursor: the next wave never uses an Ask conversation or an ablated clone as its source. Before the next ingress, all extraction batches, the integration stage, and that wave's expected evaluation pairs must be complete. The shared phase representation is an interface for the separate integration adapter; the general `stage-live` mode still rejects integration and Ask. Integration uses its own explicit mode and supervisor.

The offline report must identify `validatedPhases` as well as matching executor hashes. The integration adapter may reference the same root/phase contract, but its own validation and 4-outer/1,320-second limits require separate technical review. The present integration capacity remains the frozen product setting 30; this adapter does not change it to 50.

New CLI modes use the initial root in `MOTE_HELDOUT_ROOT_MANIFEST`, the last executor in `MOTE_HELDOUT_MANIFEST`, the same `MOTE_HELDOUT_LEDGER`, canonical `MOTE_HELDOUT_PARENT`, and matching `MOTE_HELDOUT_VALIDATION`. Ingress additionally takes `MOTE_HELDOUT_WAVE`; extraction takes `MOTE_HELDOUT_BATCH_INDEX`. `MOTE_HELDOUT_OUTPUT` must be new. Invoke the main script with the exact absolute Node binary from the initial manifest. Execute the resulting manifest with the existing supervisor; it accepts the unchanged 720-second bound and does not need parent/index flags.

Mechanical validation covers original wave-1 compatibility; missing integration/evaluation gates; rollback, skipped wave and wrong executor; normal mixed note/Coding import with exact retransmissions and a late authored date; four single-batch resumptions including cached empty output; canonical archive versus evaluation branch accounting; and generation failure followed by no later admission. Integration and evaluation milestones in this suite are explicitly mechanical ledger fixtures, not execution validation of those stages. Earlier failed attempts remain in distinct external directories. Exact final test results and hashes are delivered in the ROOT_SAFE report after all executor files stabilize.

The integration CLI is explicitly `stage-integration-freeze` / `stage-integration-live`. Freeze requires `MOTE_HELDOUT_ROOT_MANIFEST`, `MOTE_HELDOUT_MANIFEST` (previous executor), `MOTE_HELDOUT_PARENT`, `MOTE_HELDOUT_LEDGER`, `MOTE_HELDOUT_VALIDATION`, `MOTE_HELDOUT_SUPERVISOR` (the separate integration supervisor path), and a new `MOTE_HELDOUT_OUTPUT`. It delegates to `freezeIntegration` without ledger mutation. Live accepts only a heldout integration manifest and delegates with `live: true`; it does not accept a mechanical manifest or an extraction task. The separate supervisor must set `MOTE_HELDOUT_MODE=stage-integration-live` and enforce the frozen 4-outer / 300-second / 1,320-second limits. Existing 720-second supervision remains unchanged. CLI smoke verifies freezing and pre-provider rejection only; it does not claim a successful real integration or a timing test. Generic failure output conservatively retains unknown call status and references the ledger.
