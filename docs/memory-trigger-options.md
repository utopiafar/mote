# Memory 整理与洞察触发：决策备忘

> 这是实施前的调研记录。后续曾实现“定时 AND 增量”；当前代码又改为“有增量 AND（数量达标 OR 最长等待到达）”，测试规模与记录按各历史验收文档区分。实际实现与默认值见 [memory-lifecycle.md](memory-lifecycle.md)，以下历史候选不再代表当前运行策略。

调研日期：2026-09-16。状态：用户已认可混合触发方向，并倾向暴露配置、按 DeepSeek Harness 可插拔架构组织；具体默认值和以下改造尚未实施。

建议采用：**原文就绪即可检索；Memory 按增量微批提取；跨来源记忆低频整合；洞察按“周期到达且范围内有变化”运行；是否通知另行判断。**

下文中的时间、批量和频率是 Mote 的建议起点，不是行业统一标准，也没有经过本项目成本与质量实验验证。本次仅核对代码、相关历史对话与公开一手资料，没有读取生产配置、运行真实模型或采集个人数据。

## 2. 当前代码实际行为

代码基线为本工作树 `fee4fa3`。其他任务曾报告后续发布，本节仅陈述本次可核对的工作树，不据此断言生产部署的版本和配置。

| 环节 | 已实现的触发与行为 | 尚未实现或需区分的部分 |
|---|---|---|
| 通用导入 → Memory | 确认导入、记录入库完成后，为新增的当前证据创建持久任务 | 不是上传字节到达就开始抽取 |
| 手动提取 | 记忆页/API 可按范围或证据 ID 创建任务，也有旧提取 API | 与自动触发是不同入口 |
| Memory 分批 | 默认每批最多 12,000 UTF-16 字符单位、20 个片段；串行执行；每次最多 8 条候选，可返回零条 | 这是已创建任务的容量上限，不是积累 20 条输入才启动 |
| 持续采集、普通对话 | 在已核对入口中，没有统一的“每条输入/每 N 条/每小时”自动创建 Memory 任务机制 | 采集、索引或文件解析的定时器不等于 Memory 整理器 |
| 长期 Memory | `proposed / published / stale`；精确出处；来源变化失效；检查点与失败重试 | 没有完整的情景/语义分类、适用时间、跨批合并矛盾与长期整合生命周期 |
| 对话短期上下文 | 从已保存对话中选最近最多 20 轮、累计约 60,000 字符，单个旧回答最多 20,000 字符 | 是有界历史选择，不是自动滚动总结或长期记忆提升 |
| 手动洞察 | 同步入口之外，已有返回 202 的运行入口、持久进度和保存结果；重启中断标记失败 | 不宜沿用旧文档“尚无后台运行入口”的描述 |
| 定时洞察 | `MOTE_INSIGHT_INTERVAL_HOURS`，默认 0 关闭；正数用进程内计时器，每次回顾最近 N 小时 | 未检查是否新增资料；不是固定当地时刻；没有持久消费进度和停机补跑计划 |

## 3. 公开实践支持什么

这些材料展示设计模式，不证明其中任何一个产品或参数普遍最优。

| 一手来源 | 可核实的模式 | 对 Mote 的启发 |
|---|---|---|
| [LangChain Memory overview](https://docs.langchain.com/oss/python/concepts/memory) | 区分会话短期状态和跨会话长期记忆；写入可在主请求内或后台；后台支持延时、周期与手动触发 | 短期状态每步保存，长期整理单独调度；时效与延迟需要取舍 |
| [Letta Memory & dreaming](https://docs.letta.com/configuration/memory) | 后台回顾和整合，支持按完成步骤数或上下文压缩触发 | 次数与边界都是可选触发信号；不能直接把 Agent 步数等同于采集截图数量 |
| [Anthropic Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | 按需展开资料、上下文压缩和持久笔记 | 压缩当前上下文与维护长期知识是两种工作，不能只靠扩大窗口 |
| [Mem0 Add Memory](https://docs.mem0.ai/core-concepts/memory-operations/add) | 显式调用 add 触发模型抽取；平台支持异步状态和历史消息上下文 | 提取需要相关上下文，输入入库不等于推导完成。当前文档将 add 描述为追加写入，不能把旧论文中的更新算法当作当前 API 保证 |
| [Graphiti Overview](https://help.getzep.com/graphiti/getting-started/overview) | 增量情景处理、时间信息、关系失效与历史保留 | 当前事实与历史事实分别表达；先补适用时间和关系，不必立即换图数据库 |
| [Hindsight Mental Models](https://hindsight.vectorize.io/developer/mental-models) | 为固定问题维护派生答案、按范围刷新、保留溯源和历史 | 可将“项目进展”“本周变化”等设为可持续更新的专题 |
| [Hindsight 刷新 API](https://hindsight.vectorize.io/developer/api/mental-models) | 定时刷新要求范围内数据变化；按快照记录处理位置；支持合并等待中的刷新 | 与“周期 AND 新输入”的提议直接吻合；各类任务分别保存进度 |
| [Hindsight 新鲜度说明](https://hindsight.vectorize.io/blog/2026/06/17/freshness-aware-memory) | 派生层可能落后于原始事实，向查询代理暴露积压和过期状态 | Memory 没整理完，仍可查新原文；回答不能默默把旧总结当成最新状态 |

可以借鉴这些机制并继续使用现有 Harness、SQLite 和 Skills。现在没有充分理由仅为触发策略迁移整个记忆平台。

## 4. 触发方案候选

| 候选 | 方式 | 优点 | 主要代价 | 适用 |
|---|---|---|---|---|
| A：逐条输入 | 每份可读证据到达就启动抽取 | 新鲜、容易解释 | 调用频繁；碎片上下文；截图重复；多次改写同一记忆 | 低频、完整的明确记录 |
| B：纯周期 | 每小时或每天处理新增资料 | 实现简单、运行节奏可控 | 最新信息成为 Memory 较慢；须避免无变化也调用模型 | 成本优先、时效要求低 |
| C：纯数量 | 每累计 N 条处理一次 | 调用可摊薄 | 一张截图与一本书不可等量；低流量可能一直等 | 不推荐单独使用 |
| D：混合，推荐 | 增量入队，满批或最长等待到达运行；完整导入可提前启动；低频跨批整合 | 兼顾时效、完整上下文、成本与低流量 | 需要持久任务进度及少量调度配置 | Mote 多来源持续采集 |

按时间、数据量、版本和任务状态调度属于资源与生命周期管理；“哪些材料描述同一件事、哪些值得记住”仍由模型判断。不能先用关键词把资料排除在分析之外。

建议第一版参数：

| 工作 | 起点 | 说明 |
|---|---|---|
| 证据可检索 | 原文/转写就绪后立即更新索引 | 不等待记忆提取；原件未解析时只披露其可用状态 |
| 普通增量提取 | 达到一批预算，或最老待处理证据等待 15 分钟 | `有待处理内容 AND（达到批量 OR 最长等待到达）`；先沿用 12,000 字符批量上限，后续用实测 token 调整 |
| 完整文件、确认导入 | 完成后直接入队处理 | 批量仍受预算限制；大导入不挤占所有交互资源 |
| 用户明确“记住/更正” | 快速处理，展示已保存状态 | 自然语言由模型理解；宿主校验保存，不向只读查询 Agent 开放任意写工具 |
| 长期整合 | 每晚一次，仅处理新增/受影响部分 | 合并重复、保留时间变化、整理跨批关系；无需每晚全库重读 |
| 较广维护 | 每周有变化或质量问题时执行 | 校验重复、矛盾、证据覆盖与过期引用；与每周洞察是不同任务 |

15 分钟是目标入队延迟，不是模型完成时间保证。预算耗尽或失败时保留积压与原因，不能把未处理内容当成已处理。

## 5. 长短期如何整理

不把“短期”简单定义为保存几天，也不把“长期”理解为短期记录到期后搬家。

| 层 | 保存内容 | 更新方式 | 默认检索方式 |
|---|---|---|---|
| 工作记忆 | 当前目标、最近对话、已读证据、未完成事项 | 每轮/每步保存；接近有效上下文预算时压缩 | 当前会话直接使用；旧材料按需展开 |
| 情景记忆 | 一次会议、一次讨论、一天经历及变化过程 | 输入成批后形成候选；后续补充可修订 | 先读事件概要，再读时间线与证据 |
| 语义记忆 | 偏好、人物与项目关系、带适用时间的陈述 | 增量提取加低频跨来源整合 | 查当前适用陈述；历史问题展开旧版本 |
| 程序记忆 | 经验证的方法、步骤、成功/失败经验 | 在有结果与反馈时生成候选，再受控发布 | 作为经审核的方法引用，不把采集内容自动变成指令 |
| 原始证据 | 原文、截图、文件、版本与定位 | 按来源同步、修订与保留政策管理 | 支撑所有推导，不能被摘要替代 |

情景记忆可以长期保存；“短期活动”也可能形成长期有用的情景。长期化是选择与结构化，不是按年龄自动晋升。

模型需要决定：新增、合并、补充、标记矛盾、建立替代关系，或不保留。宿主验证：来源、版本、引句、时间字段、输出结构与修改范围。

不设“重复出现三次就永久记住”的硬规则：用户一次明确更正可以足够；同一内容的三张截图不能算三份独立证据。事实陈述仍需区分说话人、资料角色和不确定性。

例如：旧资料说“住上海”，新资料说“今年搬去杭州”。应记录旧陈述的历史适用范围、新陈述及二者关系；如果迁移日期不明就保留不明。如果另一个来源说法冲突，则保存冲突，不能仅按上传时间认定后来者为真。

建议增加元数据：记忆类型、主体、有效起止时间、整理时读取到的证据版本、替代/冲突关系、确认来源、原文依赖和处理位置。继续保留 `recordedAt / occurredAt / receivedAt` 的区别。

遗忘分三类：退出当前上下文、退出当前事实的默认检索、按用户政策真正删除。低频访问与年龄增长本身不构成删除原始档案的理由。隐私删除后还需要防止队列或后续重算把被删内容恢复出来。

## 6. 洞察：周期与变化相与

建议默认逻辑：

```text
允许自动分析
AND 本轮周期到达
AND 本洞察范围内有尚未处理的新增、修订或删除
AND 没有同类运行中任务
AND 有可用模型预算
```

这里的“变化”按去重后的证据版本记录，不按收到多少张截图计数。“值得呈现的新发现”是随后的模型判断，不是程序关键词筛选。只处理一条新资料，也可能得到重要洞察；不应强制凑够固定条数。

| 洞察候选 | 行为 | 适用与代价 |
|---|---|---|
| I1：固定周期必生成 | 每天必有日报 | 节奏稳定，但无数据时可能产生空报告；只适合明确要每日交付的产品承诺 |
| I2：周期 AND 有变化，推荐 | 到点检查范围内的变化，有变化才启动 | 可预期、少空跑；仍允许模型判断本轮没有新发现 |
| I3：I2 加快速通道 | 周期整理之外，模型判定重要变化可提前形成发现 | 更及时，成本和重复提示控制更复杂；建议后续再做 |

第一版可设当地时间每日 21:30 轻回顾、周日 20:00 周洞察；周日可用周洞察替代当日晚报。这些时间应可配置。

一次运行应拆开三个结果：已检查新资料、形成新洞察、通知用户。运行成功但没有新发现，也推进检查进度；不必生成 HTML 或通知。后续新资料到来，仍可结合之前的证据识别新模式。

洞察生成后先保存，由模型返回有无实质变化及证据；通知再受用户配置、频率与去重控制。低置信度推断不应被包装成确定事实。手动“立即分析”可覆盖周期限制，但不能绕过数据授权。

**时间本身改变意义的任务要单独处理。** 例如日程临近、截止日期到达，即使没有新上传也需要触发。它们使用日程/行动的时间事件；不能让所有能力都依赖“新输入”条件。历史复盘则适合上述 AND 机制。

长期 Memory 尚在整理时，洞察可以读近期原文并标注覆盖情况；不能只看已生成 Memory。采集设备离线表示资料可能不完整，不表示用户没有活动。

## 7. 实现上保持轻量，但进度必须可靠

```text
资料就绪或版本变化
  → 中央变更记录
  → Memory 提取（满批/超时/明确导入）
  → Memory 整合（低频，读取增量及相关历史）
  → 洞察（周期 AND 变化，必要时直接核对原文）
  → 保存结果
  → 通知判断
```

一套宿主持久调度即可，不需要为每个 Skill 建一个常驻 Agent 服务。复用提取任务、只读 Harness 运行时和洞察展示，增加整合 Skill 与调度状态。初期沿用 SQLite 队列；业务量证明确有需要再引入分布式调度。

- **分别消费**：Memory、日洞察、周洞察、日程发现各有处理位置。日报处理过，不应导致周报看不到资料。
- **固定本轮上界**：开始时固定证据快照和变更序号，保存结果和推进处理位置在同一事务完成；运行中到达的资料留给下一轮。需记录失败/未处理片段，不能把有空洞的最大序号当作完整处理进度。
- **晚到资料**：使用入库变更序号发现新工作，按原文发生/记录时间解释内容。今天补传上月文件会触发相应历史复核，不应被写成今天发生的事。
- **历史范围修订**：晚到、更正、删除可能影响旧报告；由证据依赖和范围标记待修订，默认合并到下一轮处理，避免连续补发通知。删除造成的不可用状态立即生效。
- **去重与并发**：同一范围、周期、Skill 版本与证据快照避免重复任务；队列中的触发可合并，正在运行后又到来的新变化不能被丢弃。
- **按需读取相关历史**：现有提取器只读本批。跨批整合需要明确的新范围授权和只读检索，不能只在提示词里要求“合并”却仍看不到旧记忆及其原文。
- **证据不自循环**：日报、周报和旧 Memory 可供导航，但不能被当成独立证据反复强化自身结论；新增事实要回到原始来源。
- **容量与预算**：交互问答优先，背景任务限并发、限输入/输出与每日费用；达到预算留待下轮。现有 Memory 1,000 条上限需要随长期整理设计一起调整。
- **重启恢复**：持久保存下次运行时刻、时区、处理位置和重试状态；重启后合并补跑，不依赖进程启动后的 setInterval 重新计时。

界面可以显示：“已归档到何时”“记忆已整理到何时”“还有多少资料待处理”“下次洞察时间”“本轮没有新发现/资料不完整/预算暂停”。“待确认”和“过期”应分别展示。

## 8. 决策建议与验收

| 决策 | 建议默认 | 可选替代 |
|---|---|---|
| 自动整理范围 | 用户启用并选定的来源；完整导入沿用当前流程 | 只处理主动上传；或覆盖所有允许的持续采集 |
| Memory 时效 | D：满批或最长等待 15 分钟，晚上增量整合 | 每小时成本优先；逐条低延迟优先 |
| 长期记忆确认 | 自动生成/整理候选；用户明确要求记住可确认；模型推断保留候选标记 | 所有候选逐条审核；或用户授权范围内自动发布 |
| 洞察节奏 | I2：每日轻回顾、每周深洞察，均要求范围内有变化 | 只做周报；或每 6 小时检查 |
| 通知方式 | 有实质新发现才提示，合并呈现 | 每期固定通知；或只在页面保存 |

先用同一组合成输入回放不同策略，比较：Memory 可用延迟、每千条证据的总 tokens/费用、重复记忆率、时态/矛盾错误率、证据可追溯率、有效洞察比例、重复通知率与队列积压。费用包含提取、整合、问答补检索和 HTML 生成，不只看回答的 tokens。

最少覆盖：只有一条输入、连续截图、大文件、同内容跨端重传、跨批偏好更正、无新资料一周、迟到历史记录、手机离线、来源删除、模型失败、任务中重启、预算耗尽。结构与恢复用 fixture 验证；语义质量用真实模型加合成资料单独验证。当前备忘不代表这些测试已经执行。

## 9. Harness 可插拔改造范围

已核对项目锁定的 `0.1.5-rc.2` 依赖、主项目已安装包的文档及官方仓库。当前查询运行时使用 `sdk-minimal`，通过 patch 加载 `mote-context` 与原生 Skill 服务，调用 `ctx.skills.register` 和 `ctx.tools.register`。这已经是 Harness 原生扩展；但 Skill catalog、统一版本号、输出模式与业务入口仍然固定。

尤其要解开 `responseMode: input.skill ?? 'answer'` 的耦合。Skill 表达分析方法；工作流指定输出契约。相同洞察 Skill 可以服务聊天文字与完整报告，新增整合 Skill 也不应迫使所有输出处理分支一起修改。

推荐采用一个扩展包、两个执行边界：

- **Harness 运行时入口**：使用原生 Cordis 插件/bundle 注册 Skills、必要的只读工具、任务提示与事件观测，通过 profile/patch 挂载。
- **Mote 宿主入口**：声明工作流、配置 schema、触发策略、结果校验与提交处理器，接入中央持久队列、证据库、计量和 UI。

同一个受信任 npm workspace 包可以同时交付两部分。工作流、触发与宿主提交声明是拟新增的 Mote 扩展协议，不是 Harness 已内置的 manifest 字段。宿主权限与证据校验始终生效，业务插件通过受控接口使用，模型只读工具集合不会因安装插件而自动获得写权限。

| 组件 | 当前基础 | 需要的改造 |
|---|---|---|
| 共享 Context 插件 | 原生插件、只读桥、证据授权与校验 | 保留公共边界，按工作流明确工具和资料范围 |
| Memory 扩展 | 提取 Skill、批处理、检查点、候选存储 | 注册提取/整合两个工作流；新增跨批整合 Skill、适用时间和替代/冲突关系 |
| Insight 扩展 | 分析 Skill、HTML/Markdown、运行记录 | 接入周期 AND 变化；允许无新发现；独立消费进度与通知策略 |
| 工作记忆扩展 | 中央对话存储和有界历史 | 按预算压缩、持久摘要和证据引用；评估复用原生 compaction 服务 |
| 中央调度服务 | Memory SQLite 队列和洞察计时器 | 统一持久触发、版本变更流、并发/预算、重启恢复和补跑 |
| 设置与运行页面 | 模型设置、部署配置草稿、任务进度 | 工作流运行配置可在线保存；显示下次运行、待处理量、跳过原因与费用 |

模型 Profile 已在主项目另一组改动中接入，计量归属正在“完善对话计量反馈与模型选择”任务中继续完善。实施时先整合相应版本，扩展工作流只引用 Profile ID，并记录 extension/workflow/skill/run 归属，不复制凭据或重新建设一套计费系统。

**原生 Schedule 与 Jobs 的边界：** [Schedule](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/schedule/schedule/README.md) 保存会话内提醒，投递依赖活跃的根 Agent；周期是固定间隔，不是完整的日历周期调度。[Jobs](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/jobs/jobs/README.md) 默认后端为进程内执行，跨进程持久后端需要重构任务身份和恢复语义。两者都不能直接替换 Mote 的常在线后台任务。中央持久调度应作为共享宿主服务供业务扩展使用；若未来需要在 Harness 会话内操作后台任务，再提供受控桥接适配。

当前 Mote 每次查询启动临时 Harness 并在结束时关闭、清理工作目录。因此定时任务、消费进度和长期记忆不能只存在这个子进程里。同理，挂上 compaction 插件并不会自动保存跨请求摘要；需要与中央对话状态一起实现。

建议先暴露启用状态、来源范围、最长等待、整理频率、洞察时间与时区、仅变化时运行、通知方式；高级项包含批量预算、模型 Profile、输入/输出预算、每日费用上限、超时、重试与并发。配置保存后供新任务使用，已运行任务固定配置/Skill/模型版本。插件代码升级先按部署重启加载，运行参数在线更新，不承诺任意代码热卸载。

改造顺序：先抽出扩展契约并迁移现有提取/洞察；再接统一变更流、混合触发与在线配置；随后加入长期整合与工作记忆压缩。初期以仓库内插件验证注册、替换、停用和版本迁移，不需先建设外部插件市场。

验收重点：增加一个使用既有结果类型的工作流时，通过注册扩展和配置就能接入，无需继续向中央入口添加专属定时器和 Skill 分支；新结果类型只增加对应处理器。停用扩展停止新任务但保留资料；版本更新不混用运行中的旧配置；重启和来源删除仍满足证据一致性要求。
