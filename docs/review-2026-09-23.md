## 性能及适用范围

测试机器为 Apple M4 / 16 GiB / macOS arm64，Node 24.15.0。测试通过实际 loopback HTTP，模型编码使用确定性向量 fixture，文件是生成字节。检索基准为 45 天、每天 200 条，共 9,000 条；第二轮同时写入的探针记录也进入实际扫描。没有通过裁掉旧数据使测试通过。

| 场景 | 实测 |
| --- | --- |
| 9,000 条、768 维检索 | 266 ms；同时健康检查/列表/写入的 p95 为 4.19 ms |
| 约 9,000 条、1536 维检索 | 395 ms；同时前台请求 p95 为 4.22 ms |
| 网页 64 MiB 提交 | 新内容 331 ms；相同内容重放 357 ms |
| 原生 100 MiB 提交 | 新内容 417 ms；重放 1,489 ms |
| 原生 512 MiB 提交 | 新内容 2,250 ms；重放 2,964 ms |
| 大文件同时前台操作 | 最差响应 133 ms；512 MiB 场景不超过 18 ms；每场景仅 2–12 次探针，报告最大值，不估计 p95 |
| 注入 50 ms 往返延迟的上传恢复 | 199 个文件与后续笔记归档、1 项隔离；完整读取 JSON 的请求 p95 为 195 ms |
| 100,000 项本地 catalog 单条更新 | 7 次 stage/ACK 中位数 1.96 ms、最大 16.19 ms；增量 checkpoint 0.75 ms |

上述结果支持此机器上、一两个月且每天几百条的测试规模可交互使用。它们不代表公网容量、多租户压力或真实手机的电量/后台保障。100,000 项仅为数据结构诊断，不是 Persona 数据集，也没有送入大模型。向量扫描仍是全范围线性扫描，规模持续增大后会触发明确降级；后续可在同一检索接口下增加向量索引插件。

## 长周期 Memory 验证

生成 Persona“林舟”维护 ORBIT 同步项目：45 天 × 每天 24 条，共 1,080 条。54 个有界 fixture 批次检查归档、执行状态、恢复和来源范围；真实模型采用本地 Codex App Server、`gpt-5.6-luna`、`max`，处理全部 45 篇主动日志，再以完整 1,080 条归档查询。1,035 条被动观察保留用于检索，没有全部送入实时 Memory 抽取。

重点验证决策变化、迟到上传、第三方归属、过期信息、未确认事件和恶意原文。已经观察到具体有用卡片：ORBIT 原始记录从 30 天改为 14 天而统计仍为 60 天；8 月 30 日 120 条记录、7 条重试后仍为 120 条唯一记录；项目评审从周二/周四改为周三 15:00；临时 connector 文档只服务 9 月 20 日演示并有明确失效时间。未确认会议不能被写为完成；一次演练通过不能推断全部设备后台同步已验证。

真实模型出现过提供方失败与 300 秒截止时间，报告保留首次失败和后续恢复。修复了宿主超时被错误归类为普通 provider error，以及有期限资料只写在描述中却未落入有效期字段的问题。超时后的显式重试现在最多按两层拆分（20→10→5），保留范围、检查点、失败历史与已完成批次；达到边界后继续明确失败，不形成无限循环。

真实生产重试路径的结果仍是 **3/4 批次完成、1 批次超时，抽取验收未通过**；45 篇日志中 41 篇已有完成检查点。已保存的 7 条候选长期记忆覆盖四个关键事实，均有精确原文及独立审核回执，临时资源的历史可见性和当前到期隐藏通过检查。这证明已产出有用内容，但不能证明 Luna Max 默认批量抽取的稳定性或延迟已达标。恢复使用保留的生成数据快照，并仅在测试副本中把已确认的旧 300 秒超时错误码迁移为新类型；不能把它称为从零开始的全默认成功运行。

自动汇总也在 300 秒截止后失败，进入可恢复等待，没有产出新卡片；这里的零产出是失败，不能解释成“模型正确选择不生成”。旧周二/周四卡片与新周三卡片仍同时出现在默认活动查询中，尚未形成成功的替代关系整理。随后一次完整归档问答耗时 115.2 秒，回答正确区分历史安排与当前安排、已验证恢复测试与未确认会议，并明确 Android 后台场景未验证。检索接口的毫秒级基准不能当成真实模型问答耗时。独立 Luna Max 评审及全部实际输出见[Persona 方法与结果](persona-memory-evaluation.md)和[生产重试记录](validation/2026-09-23/persona-production-retry.json)。

独立 Luna Max 评审耗时 143.9 秒，**5/7 项通过，整体未通过**：具体实用性、未知结果、原始时间、有效期、证据/注入防护通过；变化后的当前指导、成功的汇总收益未通过。实际旧卡片和新卡片的默认可见状态也提交给了评审。详见[评估结论](validation/2026-09-23/persona-memory-results.md)和[逐项判断](validation/2026-09-23/persona-independent-judgment.json)。

后续优先修复方向是限制单次汇总所需的模型工作量，并使模型识别的替代关系可靠进入记忆状态。当前还不能认定整个 Luna Max 记忆流水线达到稳定、可接受的性能。此次汇总的原始报告保留当时的 `workflow_failed`；根据该失败补上的错误投影修复现在会显示 `provider_timeout`，直接执行/共享执行器/重启/原退避时机的回归已通过，没有再重跑模型来改写原始结果。
