# 0.0.6 Android 升级无响应修复

## 根因与证据

用户报告在 0.0.1 留有截图后升级至 0.0.4，打开首页无响应，随后被系统终止。本次没有读取用户手机或个人截图，也没有该次退出的系统 ANR trace，因此不能把代码定位表述为已取得真机故障日志。

对比版本代码发现明确回归：0.0.1 的 `DurableQueue.pendingSync()` 仅枚举文件，`bytes()` 仅累计文件长度；0.0.2 引入延后 OCR 后，两者各自逐条解密所有 `.event` 以计算上传状态与 OCR 空间预留。0.0.4 的 `MainActivity.refreshStatus()` 在主线程每两秒调用这两个方法。一轮刷新对 N 条旧记录产生约 2N 次 Android Keystore 解密，并持有全局队列锁；诊断采样还可能增加等待。`recovering` 只保护启动恢复期间，无法保护恢复结束后的刷新。

采集服务的主线程 tick 也通过 `canCollect()`、heartbeat 同步进入相同队列统计。此类主线程长时间等待符合 ANR，`runCatching` 无法捕获系统的 ANR 终止，也不保证产生 Java crash 日志。普通旧版升级的存储位置初始化只增加标识和位置指针，不会批量重编码图片；此次没有发现必须删除旧数据的格式问题。

## 修复

- 首页在单任务后台执行器读取状态，主线程只应用结果；重复请求合并，暂停/销毁后丢弃晚到的页面更新。
- `QueueStats` 单次扫描提供数量、磁盘占用、OCR 预留和待同步状态。进程内有界缓存仅保存每条事件的固定统计元数据，未变化事件无需再次解密。新增、原子替换、OCR、确认和删除主动失效对应缓存，目录迁移隔离缓存。缓存不保存截图或正文，不替代完整性验证；损坏仍报错并保留文件。
- 采集的诊断和空间预检移入原有处理执行器，仍在模型/OCR 前检查，入队仍作最终容量校验。满空间时可能接收一帧至内存，但不会新增记录。
- 同步与来源调度在后台执行并限制积压；同一配置的显式同步意图保留，不将旧节点的显式意图转移到新配置。
- 设置应用后的存储验证、手动同步和诊断导出在后台等待存储。

## 验证

- 最终 Android JVM 测试共 81 项，0 失败、0 错误、0 跳过。新增 5 组队列统计测试与 3 组调度合并测试。
- 250 条旧格式事件的计数 fixture：第一次统计解密 250 次，随后跨队列实例的重复统计不新增解密；完整性校验仍重新读取全部事件及图片。覆盖 OCR/确认/冲突/迁移、损坏和相同大小/时间戳的原子替换。
- 调度 fixture 在处理期间提交 10,000 次请求，只产生一个合并后续任务；同配置显式请求保留，切换节点/策略不会继承旧的显式上传意图。
- `lintRelease` / `lintDevelopment` 均 0 错误，分别仍有 114 / 121 条警告；不宣称零告警。Development APK 与测试 APK 构建成功，实际证书 SHA-256 为 `0670a89e6f9548552b90777dd1e0dc4e3efab6cf7082d436fcc60d6e9edb5076`，16 KiB ZIP 对齐通过。
- 专用 `mote_fixture_api35` / API 35 arm64 模拟器执行 `AnrRegressionInstrumentedTest` 3 项、`ServiceResponsivenessInstrumentedTest` 2 项、`SettingsStorageInstrumentedTest` 4 项、`NavigationInstrumentedTest` 4 项，最终 13 项全部通过（12.237 秒）。队列恢复标志已清除但全局锁被后台占用时，首页启动、四页导航与销毁不等待队列；30 次刷新只应用一次状态，销毁后不写页面。采集 eligibility 与同步调度在相同持锁条件下 1 秒内返回。
- 使用真实 Android Keystore 加密的 256 条生成 v0.0.1 事件和 JPEG，验证恢复后文件逐字节散列不变、旧 OCR 不会新增延后 OCR 空间预留、首尾图片可读。

所有 fixture 使用生成事件、图片和配置；未开启真实屏幕采集或调用模型。

## 范围

未执行用户手机、HyperOS、真实投屏会话、真实截图采集或长期后台耗电检查。旧格式数据验证与真实旧 APK 到新 APK 的覆盖升级是不同的验证，本轮不宣称已执行后者。
