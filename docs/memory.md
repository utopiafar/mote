# Memory and evidence retrieval

Memory is selected, model-derived context with a subject, scope, time, provenance and uncertainty. It may describe a preference, subjective experience, provisional interpretation or engineering decision. Automatic publication does not make it independently verified fact. Retained originals remain retrievable whether or not they produce Memory; an owner can release an original independently of its valid published Memory.

The [product principles](product.md) define the direction; the [architecture gaps](architecture.md#product-direction-and-implementation-gaps) distinguish it from current code. In particular, the model may use valid Memory directly and decide when to verify it. Extra semantic review follows the selected Memory recipe: a pinned reviewer requests an independent pass, while explicit `review: null` uses host-validated extraction directly. No keyword routing chooses between these paths.

## Classification and attribution

`admission.layer` separates `observation` (events, document summaries and task leads) from `memory` (selected useful context). Its reason, scope and attribution explain what the result is for and whose statement it represents. Domain, extraction/consolidation tier, kind and publication status are separate fields; a published observation is not thereby a personal fact.

Models interpret meaning using continuous source context and owner-provided background. Source type does not determine meaning: a Coding Agent conversation can contain personal experience, technical decisions and an ordinary task lead. A third-party interview in the owner's archive is not the owner's opinion. Repeated experiences can be useful without becoming a permanent personality label. Reported fixes and Agent claims keep their unverified status.

Source project identity is structured metadata: workspace, session fallback or unknown. It does not assert that every discussed project is the source repository. Preserve subject and source rather than inventing a dedicated identity-confirmation flow. Background uncertainty can remain recorded; clarify when it matters to the current answer or action, remembering earlier answers and constraints.

## Current processing path

1. A durable manual request or automatic receipt authorizes exact inputs and pins the recipe, strategy versions and source state.
2. Extraction reads bounded targets and may request relevant interpretation context within that grant. Models select useful candidates; zero candidates is valid.
3. A recipe with a reviewer independently reviews the candidate set and coverage, including empty results. A recipe with `review: null` validates extraction directly and still checks applicable deletion intent. A native implementation using this path must already return the canonical Mote output contract. Integration recipes retain their selected reviewer.
4. The host checks current permissions, original versions, exact quotes/ranges, dependency validity and deletion state, then commits publication and checkpoints atomically.

Coverage names the target ranges actually assessed. `checked` and `no_candidates` mean complete assessment of those targets, not of an entire file or session. Unread, truncated or unavailable content remains incomplete. No candidate-count quota or keyword semantic classifier substitutes for model judgment. Interpretation context does not itself authorize candidates or count as target coverage.

Saved quotes require exact support, not fuzzy matching or OCR correction. The host may locate an omitted offset only when the identical substring is unique in the permitted range. Current Memory uses the strict schema, including classification, version, fingerprint and evidence content hashes; readers do not manufacture missing metadata for old records.

New accepted results become effective without owner approval of every card. The owner can correct, explicitly publish an eligible proposal or delete results. Those commands recheck current evidence and deletion intent; they are not a compatibility route for malformed old records.

## Jobs, recipes and recovery

Strategies and recipes are replaceable through [memory-strategy-contract.ts](../apps/server/src/memory-strategy-contract.ts). Definitions, fingerprints, input requirements and receipts are pinned. The review decision is part of the recipe and binding fingerprints. A changed reviewer can reuse an extraction draft but needs a new matching review; changing the decision cannot change an already pinned task or authorize its late result. New defaults do not rewrite an existing task or retrospectively authorize old inputs.

The existing personal, Coding and daily-event recipes retain their independent reviewers and remain the defaults. `mote.personal-memory-direct@1` is a separately selectable personal recipe without an extra semantic review. It is listed by `/api/memory-recipes` and selected through the existing `/api/memory-recipe-settings` owner command, including source overrides. Direct publication records `decision: not_required`, the selected recipe pin and `validation: host-evidence@1`, with no reviewer run ID. It remains model-derived context, not independently verified fact. Provenance-matched deletion intents may still require a semantic comparison to prevent regeneration of a deleted conclusion; this is not a fixed per-batch review.

Memory work packages put the exact target originals and their stable context before the stage instructions and draft. Optional original ranges stay in the authorized catalog. The reviewer starts with the same target originals and reads any needed background through its own authorized context tools. Previously published cards and completed checkpoints remain usable under their current source and policy pins. A source revision invalidates dependent work and cards for the affected ranges.

A bounded validation error can request a replacement for one candidate, coverage row or evidence entry. Central assembles the result with the other rows and repeats the full validation before publication. Reviewed text recipes can return edits to a non-empty, validated draft when candidate order and coverage identities stay fixed. Changes to the candidate set can use the full output. Every independent review still validates the complete target set, including an empty draft. Use source recipe overrides to compare independent review and direct publication on representative originals before changing their defaults.

Manual input plans separate an original source pin from derived readiness. Each material/recipe pair uses a durable `memory.input` execution step. Pending OCR/transcription waits before claiming a model attempt; failed inputs need explicit retry, and retrying Memory does not start media processing. Completed independent batches remain reusable. Cancellation, an explicit job pause, source replacement or revoked permission prevent unfinished work and late publication. Metadata binding and step creation share one fenced transaction.

Newly authorized ready inputs use rolling packages; older lifecycle windows retain their own cursors and bounded drain policy. Ordinary pause closes new Memory intake while previously authorized original receipts, claimed jobs and frozen lifecycle rounds can drain across restart. Resume retains those exact grants and their checkpoints. Unregistered lifecycle events, including the paused gap, are retired after any retained finite round; they are not reported as completed work. A duplicate delivery or resume command cannot authorize previously denied Memory input. Immediate stop revokes existing automatic receipts and the unfinished round, cancels its active work and fences late publication; independent manual work remains authorized.

Memory intake authorization is separate from source reading and background model disclosure. Recovery rechecks current source state, privacy, recipe pins and model permissions. It does not scan historical originals or mint replacement receipts. Integration, insights and working context retain separate schedules. Waiting inputs and owner questions do not occupy model slots. Persistent checkpoints survive restarts; a timeout may recompute unfinished work while retaining completed valid stages and the original bounded retry budget.

Accepted model plans attribute their actual Memory product operations to the existing shared execution projection. The status link and parent membership commit together; bounded reconciliation restores an interrupted handoff without duplicating steps or receipt claims. Parent progress includes the product's real input, batch and phase steps, so finishing a planner does not report an unfinished product as complete. A failed product parks its status bridge before spending a control attempt, allowing an explicit product retry to rejoin while retaining successful stages and their model budgets. Memory and delegation keep their own private domain products. Ordinary ready-input packages continue to use capacity packing without a mandatory planning call; model-selected plans retain their pinned package and recipe decisions. See [memory-delegation.ts](../apps/server/src/memory-delegation.ts).

The existing shared owner-question service retains versioned questions and responses. Obsolete source, binding or authorization state retires a question. An answer can support a continuation; it cannot certify identity or publish a draft by itself. This service should support necessary clarification without interrupting every uncertain background interpretation.

## Query and disclosure

`EvidenceReader` is shared by Web, MCP and the Agent bridge. It does not remember prior authorization; every read applies current credentials, source/device/time scope, privacy and deletion state. Context navigation refs describe a query, not a grant. Reconstructing one still checks the original anchor, and a deleted anchor cannot silently resolve to a newer head.

| Read | Result |
| --- | --- |
| Memory list | Bounded cards, metadata and continuation cursor. |
| Memory detail | Statement, uncertainty and source locators. |
| Optional source evidence | Verified original ranges with offsets, delivery provenance and explicit partial-coverage information. |
| Original/material read | Paged current or pinned evidence; unavailable retained text returns its known location and reason without reading an offline device. |

Public evidence refs use explicit `capture:<UUID>` or `memory:<UUID>` namespaces. Resource URLs whose schema declares an ID still use UUIDs; adapters perform the conversion. Derived artifact refs pin `artifact:<encoded-id>:<encoded-revision>`. Ref spelling or a saved locator grants neither access nor citation authority.

A model can reason directly from useful valid Memory within its subject, attribution, applicability, time and uncertainty. It decides when a material gap, conflict, potentially outdated state or visual question needs deeper reading. A quotation or claim about what a particular source says needs that authorized original content. Exact quotations and original citations require the actual authorized original range to have been delivered successfully in this run. A Memory locator or an old stored quote does not establish that delivery. There is no compulsory traversal through every layer or redundant read of an already delivered range.

Dependency checks include every original behind Memory and derived artifacts. An exact current Material anchor can prove delivery without exposing raw recording ancestors, while their source/privacy/deletion permissions still apply. The reader does not treat one covered member as covering every separate citation. Literal search supports stable exhaustive pagination; ranked retrieval is bounded and may be incomplete. Empty or filtered pages are not proof of absence.

Image disclosure is a separate host setting and is disabled by default. A selected image target must actually reach the relevant model, including an independent reviewer when that review is used; text/OCR does not establish visual coverage. Context-only images remain optional. Missing capability, disabled disclosure or failed delivery stays explicit, rather than dropping the target or claiming it was assessed. See [processing](processing.md#images).

## Publication, deletion and replacement

Models may explicitly select `contextPriority: "standing"` for an important preference or constraint that should remain available across requests. The field passes through extraction, selected review or direct publication and the Memory fingerprint. It is not inferred from tier, kind, source, wording or recency, and existing records are not rescored or backfilled. Owner corrections preserve it unless explicitly changed; `contextPriority: null` on the owner correction command clears it.

Opening context pages all currently authorized, effective standing Memory and keeps its full claim, scope and uncertainty alongside a bounded ordinary navigation sample. Newer ordinary cards cannot displace standing items. Parent research continuations retain standing context when resuming from a saved workspace; research children retain their existing context isolation. The actual configured model budget checks the complete request. If standing context and required reserves cannot fit, preparation fails before model dispatch instead of silently dropping cards or clipping their qualifications; the saved failure retains the existing `contextWindowExceeded` diagnostic. Current permissions, revisions, validity, corrections and deletion dependencies are rechecked before model use and publication.

Standing context is derived evidence, not an owner system instruction or Action authorization. A third-party constraint remains attributed to that person and its stated scope. Background uncertainty can remain recorded; the model asks only when a missing fact materially affects the current user goal and respects applicable prior answers and refusals.

Only currently valid published Memory enters ordinary Agent queries; historical/proposed/stale views remain explicit owner reads. Current source revision changes make dependent cards stale. Owner deletion of a capture original, its complete authored Material alias or a central file archive releases original bytes and parsed text while preserving Memory already published from that evidence. It does not authorize an unfinished extraction, revive a retired receipt or change conversation-retention policy. Central file history deletion still rejects deleted and already-admitted old versions while accepting genuinely future versions; explicit file forgetting additionally suppresses future versions until allowed again.

The release transaction records only the published Memory IDs and fingerprints plus the original source/device/time, collection and authorization identity in the existing evidence-revocation outbox. It keeps neither original text nor image data in that metadata. Every later Memory read still checks current scope, source identity, exposure routes and source declarations. A released dependency can satisfy existence only for its recorded published card, not a new extraction or a naked original ID. Current dependency checks keep each retained card and its ancestry together across authorization yields. Memory details mark that reference `originalAvailable: false` and omit saved quotes and original ranges. Original reads remain unavailable; the Agent can use the scoped claim but cannot cite a vanished original as delivered evidence.

Interactive queries record Host-computed `originalEvidenceDependencies` separately from Memory ancestry, including a positive empty set only when complete Host delivery was observed. Confirmed original text and image delivery still require strict current checks, even when the same original also supports a valid Memory and the final answer has no citations. The Host overwrites any Agent-supplied role receipt. Saved dialogue retains Memory refs for proven Memory-only context; its original roles independently follow the existing history/retired-proof policy and current permissions. Unknown older receipts keep their conservative original dependency behavior.

Deleting a Memory remains an explicit refusal to regenerate that conclusion, including when its originals have already been released. The existing deletion ledger retains identity and derived intent without retaining original quote text. Explicit file/source/Material forgetting and privacy invalidation still revoke matching Memory, including dependencies whose original rows are gone. Deleting the last owning import also withdraws its source and Memory; a different import sharing that source retains its existing originals and Memory. Corrections and source replacements withdraw the former claim from current use. Provider cleanup erases revoked or unpublished late writes while retaining the exact bodies of cards published before ordinary release.

Portable archive version 2 includes the canonical `memoryOriginalReleases` metadata section. It preserves scope and deletion identity without restoring original bytes. Imported Memory remains stale, as with other portable Memory; imported release metadata cannot authorize original reads, Agent use or publication. The current MVP has no day-based cleanup scheduler.

Deletion intent survives retries and regeneration. Deleting one card invalidates dependent cards; it does not erase unrelated source originals. An external provider erase is durable work with reconciliation: a lost response is unknown, not success. The host retains admission, authorization, version checks and publication transactions even when storage, search or a native semantic stage is replaced.

Provider bindings prepare, verify and switch exact namespaces, keys, versions and bodies before changing the active reader. Failed preparation retains the previous binding. A native engine produces an untrusted draft; it does not inherit owner commands or publication authority. Process isolation is not a sandbox for hostile native plugins.
