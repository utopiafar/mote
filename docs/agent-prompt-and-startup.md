# Bounded prompts and startup measurements

Both Codex and Harness use the same stable safety/task core. A query restricted to explicit evidence IDs can omit source-protocol rules absent from those records; open-archive queries and unknown protocols retain all rules. This dispatch uses source types and explicit metadata fields, never semantic keywords in captured text. Tool limits, exact evidence scope, read-only access and injection handling remain unchanged. Fixed semantic extraction has its own bounded structured products.

The live comparison uses generated notes, a fixed clock, the same read-only evidence tool and local `gpt-5.6-luna`. The initial three paired cases cover a proposed event with injected instructions, third-party attribution/project scope, and a partial correction. Two passed both variants. The third exposed an unsupported display-time-zone inference in the bounded answer; the original prompt instructed the model to name the display zone for every clock time. The shared core now distinguishes converted observation timestamps from authored times whose zone is unknown. The affected pair and its independent judge passed after that correction. The two remaining cases were then rerun against the final core in separate reports with independent judgments; both variants passed in both cases.

- Initial paired inputs: 15,244 → 13,996 tokens; totals: 15,699 → 14,498. The failed case remains in the report and these numbers are **not** a passing quality benchmark.
- Corrected case inputs: 5,119 → 4,703 tokens; totals: 5,284 → 4,930. Both retain the unchanged proposal and distinguish plans from attendance. These are actual complete cumulative thread receipts. Internal request counts remain unknown, and no configured provider price was used to invent a monetary cost.
- Final proposal/injection case inputs: 5,108 → 4,692; totals: 5,254 → 4,847. Final author/scope case inputs: 5,092 → 4,676; totals: 5,192 → 4,809. All three cases now have a passing comparison on the corrected core. Aggregating those separate runs gives inputs 15,319 → 14,071 and totals 15,730 → 14,586, excluding the three independent judges. These are token measurements, not monetary-cost measurements.
- The bounded source assembly removes 2,317 prompt characters per fixture. This small generated sample demonstrates the mechanism; it does not establish general accuracy or latency improvement. Reports include the independent judgments, answers and measured usage.

The final proposal pair took 12.93/13.77 seconds and the author pair 11.16/11.38 seconds (all-source/bounded), including fresh session startup. The bounded author answer reported 3,840 cache-read tokens; the other final answer receipts reported zero. There is no measured answer-latency improvement in these two samples, and differing cache state makes a broader speed claim inappropriate. Each report's judge is a separate actual model session, not a deterministic acceptance heuristic.

The separate startup benchmark launches four fresh actual Harness sessions against generated local HTTP replies. First-provider-request times were 347.1, 339.7, 344.0 and 332.3 ms; total times 401.8, 385.8, 394.5 and 372.3 ms. Two profiles use distinct credentials and evidence scopes, checked at the provider boundary. Sessions are not pooled or shared, so this is a startup baseline and isolation check, not a claimed warm-session speedup. HTTP response usage in this fixture is explicitly synthetic.

## Shared resource admission

ExecutionEngine admits durable steps by resource pool and least-recently-served Operation. Finishing one step starts another without waiting for a slow sibling. Provider sessions use the same explicit Operation key in their bounded concurrency gate; interactive and background pools each retain capacity. The smallest mixed fixture holds one OCR step while a small file operation, Memory work and an interactive query all finish. Larger existing fixtures run 400 interleaved operations and verify capacity across two database connections. This bounds concurrency and demonstrates progress; it does not preempt an in-flight provider request or promise a latency SLA.
